\section{Introduction}

Making a server fault-tolerant without rewriting it is \emph{transparent} fault tolerance, a four-decade
goal that has repeatedly failed to reach production. The reason was never the snapshot; checkpointing a
process is well understood. It was three \emph{coupled} costs a transparent system pays on the critical
path, each a large fraction of latency at the operating point every prior system lived at:
\begin{enumerate}[leftmargin=1.4em,itemsep=1pt,topsep=2pt]
\item \textbf{Logging non-determinism.} To replay a recovered replica to the exact
  state of the failed one, every non-deterministic event must be recorded, above all the
  \emph{order} in which concurrent messages were processed. Order logging is the dominant
  per-event overhead of deterministic replay~\cite{mashtizadeh2017castor,ocallahan2017rr}.
\item \textbf{Coordinating a consistent cut.} A snapshot of a distributed system must be
  globally consistent. The classical mechanism is Chandy--Lamport marker
  propagation~\cite{chandy1985snapshots}, which captures in-flight channel state.
\item \textbf{Output commit.} Output that has become externally visible cannot be un-sent
  on recovery, so a transparent system must \emph{withhold} each externalizing message
  until the state that produced it is durable~\cite{strom1985optimistic}. This output-hold
  is what sank Remus~\cite{cully2008remus}: tens of milliseconds of latency on every reply.
\end{enumerate}

Faced with these costs, the industry chose the \emph{other} path: rewrite applications to externalize
state into a system fault-tolerant by construction, through durable execution (Temporal~\cite{temporal},
DBOS~\cite{skiadopoulos2021dbos}, Restate~\cite{restate}) and exactly-once stream processing
(Flink~\cite{carbone2015flink}). That path won mindshare one rewrite at a time, but left the legacy fleet
behind: stock Redis, Memcached, Nginx, application servers, and databases, whose rewrite is exactly the
cost transparent FT was meant to avoid.

\paragraph{This paper.} We revisit the abandoned transparent path and show it becomes practical under two
co-designed shifts, neither sufficient alone.

The \textbf{first} is a user-space \emph{determinism libOS}: an \texttt{LD\_PRELOAD} shim (no kernel, no
application changes) that makes an unmodified server deterministically recoverable by virtualizing its
residual \emph{local} non-determinism, the clock, the random source, and thread-scheduling order. Once
message order is supplied externally this residual is small and closable: stock Redis, Memcached, Nginx,
Node.js, and a multi-process PostgreSQL recover \emph{byte-identically} across a crash and a real-time gap
at a few-percent overhead.

The \textbf{second} is the operating point. Prior transparent systems paid the three
costs over software-ordered, TCP-scale, hypervisor-logged \emph{millisecond} paths, where
each was a large fraction of request latency. If instead all communication of
\emph{share-nothing} servers is routed through an in-network total-order \emph{reliable}
fabric, the three costs do not merely shrink; they \emph{change structure}. That fabric is
1Pipe~\cite{li2021onepipe}, which establishes total order in a programmable switch and
delivers reliably via a two-phase commit barrier over an RDMA fabric whose round-trip is
$1$--$2\,\mu s$:
\begin{itemize}[leftmargin=1.4em,itemsep=1pt,topsep=2pt]
\item The fabric \emph{is} the order, so the replay order-log vanishes.
\item A timestamp-$T$ snapshot replaces the Chandy--Lamport cut, and is in fact stronger,
  because an order-preserving fabric has no in-flight channel state to capture.
\item The output-commit barrier \emph{is} the fabric's reliable-delivery commit barrier,
  so the durable-replica write completes under a barrier the system already pays for, and
  fault tolerance adds no round trip.
\end{itemize}
The single new engineering idea is the last point. OneBarrier replicates its recovery log
via 1Pipe's native 1-RTT replication, scattering each input to the backups at its
total-order position; that replication completes \emph{within} the $1.5$-RTT
reliable-delivery barrier the output-commit hold already waits for. At the millisecond
scale this overlap saves little. At $1$--$2\,\mu s$ RTT it is the difference between fault
tolerance being a tax on every reply and a byproduct of the fabric.

\paragraph{Scope, stated up front.} This is a realization-and-measurement result, not a new
primitive, and three boundaries define it. (i) The conceptual idea is anticipated:
LLFT~\cite{zhao2013llft} did transparent, order-log-free FT of unmodified socket applications via
totally-ordered virtual time, and HyCoR~\cite{zhou2021hycor} did checkpoint-replay of unmodified
containers; our contribution is the co-design with an \emph{in-network} fabric and the
demonstration that the cost \emph{regime} changes at the microsecond operating point
(\S\ref{sec:novelty}). (ii) Everything but the barrier magnitude is measured on stock binaries; the
barrier coincidence is an architectural identity (\S\ref{sec:overview}) whose RDMA \emph{magnitude}
is established by a discrete-event model at the published operating point and corroborated by real
RDMA verbs over software RoCE, not a hardware testbed (\S\ref{sec:eval-overlap}). (iii) Durability
is in-memory $f$-of-$k$ fail-stop tolerance via in-fabric replication, not crash-consistent
persistence across correlated power loss (the FaRM/RAMCloud tradeoff~\cite{dragojevic2014farm}).

\paragraph{Contributions.}
\begin{itemize}[leftmargin=1.4em,itemsep=1pt,topsep=2pt]
\item A transparent determinism libOS that closes the local-non-determinism boundary
  (time, randomness, threads) for real unmodified servers and recovers stock Redis,
  Memcached, Nginx, and Node.js \emph{byte-identically by deterministic replay}, plus a
  multi-process PostgreSQL via CRIU (\S\ref{sec:libos}, \S\ref{sec:eval-recovery}).
\item The structural argument, and its measurement, that an in-network total-order reliable
  fabric collapses the three coupled costs by construction: the output-commit hold and the
  fabric's reliable-delivery barrier are one barrier, so FT adds no round trip
  (\S\ref{sec:overview}, \S\ref{sec:eval-overlap}).
\item An end-to-end evaluation on stock binaries (byte-identical recovery, linearizability
  and exactly-once under crashes, bounded recovery time and overhead, resource cost against
  same-engine HyCoR-style and LLFT-style mechanism baselines, active state-machine
  replication (SMR), and CRIU), carried by an explicit fit-test to ten further applications
  across five classes (\S\ref{sec:eval}, \S\ref{sec:ext}).
\item Machine-checked TLA+ specifications of 1Pipe total order and of OneBarrier's
  exactly-once recovery, and a candid novelty reckoning (\S\ref{sec:impl},
  \S\ref{sec:novelty}).
\end{itemize}

\section{Why Transparent FT Failed, and What Changed}
\label{sec:why}

\paragraph{The three coupled costs.} A transparent FT system must, on every externalizing
message, guarantee that the producing state is recoverable. Three mechanisms make that
guarantee, drawn from the classical rollback-recovery toolkit~\cite{elnozahy2002survey},
and each was historically expensive (Figure~\ref{fig:threecosts}). \emph{Deterministic
replay} reconstructs a failed replica's state by re-executing its inputs in the same order;
that order is non-deterministic and must be logged, and message-order logging dominates
replay overhead~\cite{mashtizadeh2017castor}. A \emph{consistent distributed snapshot} lets
a recovered replica resume from a globally coherent point; Chandy--Lamport
\cite{chandy1985snapshots} achieves it by injecting markers and recording channel state.
And \emph{output commit}~\cite{strom1985optimistic} forbids releasing output until its
producing state is durable. Remus~\cite{cully2008remus} paid this last cost as tens of
milliseconds of buffered output; VMware FT~\cite{scales2010vmwareft} paid the order cost as
lock-step execution. At the millisecond scale all three were a large fraction of request
latency, which is why transparent FT never displaced application-level replication.

\begin{figure}[tb]
\centering
\includegraphics[width=0.60\linewidth]{figures/fig_threecosts.pdf}
\caption{The three coupled costs that doomed transparent FT at the millisecond scale, and
how each collapses: the fabric kills the order-log, the distributed cut, and the
output-commit hold; the determinism libOS kills the residual local non-determinism.}
\label{fig:threecosts}
\end{figure}

\paragraph{The 1Pipe fabric.} 1Pipe~\cite{li2021onepipe} provides \emph{scalable
total-order} communication: messages carry timestamps, an in-network barrier aggregation on
a programmable switch establishes one global order, and a FIFO gate delivers in timestamp
order. Its \emph{reliable} mode is a two-phase commit: end-to-end loss recovery, then an
aggregated \emph{commit barrier} that makes a group delivery atomic, one extra round trip
over best-effort. It also replicates natively: a client scatters a record to all replicas
at a single total-order position in one round trip. The fabric therefore \emph{already}
establishes order, \emph{already} crosses a commit barrier, and \emph{already} replicates,
three mechanisms it provides for communication correctness alone, at a microsecond RDMA
operating point where each is set by the network rather than by software
(parameters in Appendix~\ref{app:model}).

\paragraph{The operating-point argument.} Our claim is not that the idea is new but that the
\emph{cost regime} is. Once order is established in the switch and replication completes under a barrier the
communication layer already crosses, each cost becomes a structural consequence of the fabric, paid for
communication correctness whether or not the system is fault-tolerant. This is a design conclusion, not a
hardware speedup: the RTT sets only the magnitude of a margin that is zero in structure. Transparent
passive FT is free at the reliable-fabric baseline at any RTT; the microsecond operating point is what
makes that \emph{matter}.

\section{Overview: Fault Tolerance as a Byproduct of the Fabric}
\label{sec:overview}

Figure~\ref{fig:arch} shows the architecture. An unmodified share-nothing server runs over
the determinism libOS, which intercepts its POSIX surface: sockets are routed to the 1Pipe
fabric, and local non-determinism (time, randomness, thread order) is virtualized so that,
given the same input sequence, execution is a deterministic function of that sequence. The
fabric supplies the input order and a reliable-delivery commit barrier; an in-fabric replica
supplies durability, because each input is scattered to it in one RTT and is durable by the
time the commit barrier passes.

\begin{figure}[tb]
\centering
\includegraphics[width=0.58\linewidth]{figures/fig_arch.pdf}
\caption{OneBarrier: an unmodified server over the determinism libOS over the 1Pipe fabric.
The fabric supplies the order and the reliable-delivery commit barrier. The recovery log is
replicated by scattering each input to an in-fabric replica (1Pipe's 1-RTT replication),
durable by the time the commit barrier passes. The libOS supplies local determinism,
deterministic replay, and output suppression.}
\label{fig:arch}
\end{figure}

The fabric pre-pays, for communication-correctness reasons, for exactly the three things FT
needs. Each collapse below is a structural identity, not an optimization: the mechanism FT
requires and the mechanism the fabric already runs are the same mechanism.

\paragraph{(a) Order $\Rightarrow$ no replay order-log.} Because 1Pipe delivers messages in
a global timestamp order, the recovered replica re-applies inputs in \texttt{msg\_ts} order
with no recorded order-log. The dominant cost of deterministic replay is removed not by
optimization but by relocation: the order lives in the fabric. This is the
state-machine-replication property~\cite{schneider1990smr} realized over an in-network order
source.

\paragraph{(b) Timestamp-$T$ snapshot $\Rightarrow$ empty-channel cut.} To snapshot, the
libOS quiesces at a barrier timestamp $T$: it stops dispatching inputs with \texttt{ts}~$>T$,
drains in-flight handlers for \texttt{ts}~$\le T$, and checkpoints. Every message is, by the
identical \texttt{ts}~$\le T$ predicate, on the same side of the cut at sender and receiver,
so the cut is consistent with \emph{no} marker propagation and \emph{no} captured channel
state. It is strictly simpler than Chandy--Lamport, and uncoordinated: each node applies the
same predicate independently.

\paragraph{(c) Output-commit $=$ commit barrier.} A server's reply is withheld until its
producing state is durable. OneBarrier replicates the recovery log by scattering each input
to the backups at its total-order position (1Pipe's 1-RTT replication), and holds the reply
until the reliable-delivery commit barrier, the second phase of 1Pipe's 2PC, passes that
input's timestamp. The fabric crosses that $\sim\!1.5$-RTT barrier regardless of fault
tolerance, and the 1-RTT replication completes inside it (Figure~\ref{fig:barriertimeline}).
These are not two barriers that overlap; they are the \emph{same} barrier, so FT adds no
round trip, a margin zero by construction. The RTT sets only how large the avoided cost
\emph{would} have been; \S\ref{sec:eval-overlap} quantifies the magnitude.

\begin{figure}[tb]
\centering
\includegraphics[width=0.56\linewidth]{figures/fig_barrier_timeline.pdf}
\caption{The barrier coincidence, by construction. The recovery-log replication ($1$\,RTT)
completes \emph{inside} the reliable-delivery commit barrier ($1.5$\,RTT) the fabric crosses
for communication correctness regardless of fault tolerance, so the producing input is
durable before output may be released. The output-commit hold and the reliable-delivery
barrier are the same barrier; FT adds no round trip, independent of the absolute RTT.}
\label{fig:barriertimeline}
\end{figure}

What makes (c) work in practice is (a)+(b)+the libOS: the recovered replica is a
deterministic function of the fabric-ordered input prefix up to the last durable barrier, so
``the producing state is durable'' reduces to ``the input prefix is replicated,'' which the
fabric already does.

\section{A Transparent Determinism libOS for Unmodified Servers}
\label{sec:libos}

The fabric supplies order; the libOS must supply everything else an \emph{unmodified} binary
needs to replay deterministically. It is three composable \texttt{LD\_PRELOAD} libraries
totalling $\sim$1{,}000 lines of C, in the SocksDirect~\cite{li2019socksdirect} kernel-bypass
lineage, with no kernel module and no application change.

\subsection{The determinism boundary}
Once message order is external, a server's remaining non-determinism is \emph{local}: values
it reads from the clock and the random source, and, if multi-threaded, the order its threads
interleave. We found, and the libOS closes, a sharp boundary between two kinds of time read
(Figure~\ref{fig:boundary}). \emph{Request-driven} reads (one per request, e.g.\ a timestamp
stamped into a reply) replay correctly by sequence position. \emph{Timer-driven} reads (a
background timer firing on wall-clock, e.g.\ Redis's \texttt{serverCron}, Nginx's cached-time
update, Memcached's LRU maintainer) fire a \emph{different number of times} between record and
replay, desynchronizing any position-indexed scheme. The virtual clock closes this boundary by
making time a function of the input prefix rather than of read count or timer firings.

\begin{figure}[tb]
\centering
\includegraphics[width=0.50\linewidth]{figures/fig_boundary.pdf}
\caption{The determinism boundary. Under wall-clock time a background timer fires a different
number of times between record and replay, so timer-driven reads desync (left). The virtual
clock advances one tick per input event, making every time read count-independent and
identical across recovery (right).}
\label{fig:boundary}
\end{figure}

\subsection{Virtual clock: time virtualization}
The libOS intercepts the libc time surface (\texttt{gettimeofday}, \texttt{clock\_gettime},
\texttt{time}) and returns \emph{virtual} time $t = \mathrm{base} + \mathrm{ticks}$, where
\texttt{ticks} advances only at a socket read, so the value is a \emph{count-independent} function
of the input prefix: how many times, or from which timer, it is read does not matter, which is
what stops a timer-driven read from desyncing replay. We advance by the \emph{real inter-arrival
delta}, logged per input, so virtual time tracks the wall clock at record and the recovered run
replays the same deltas: wall-clock-faithful \emph{and} byte-identical, unlike a fixed delta that
would expire TTLs on an input-count schedule. Over the real fabric the message's own total-order
timestamp \emph{is} that logged, replicated source, so virtual time is just
$\mathrm{base} + (\texttt{msg\_ts} - \texttt{msg\_ts}_0)$ (Appendix~\ref{app:libos},
Listing~\ref{lst:vclock}). The sharpest demonstration is Nginx: the HTTP \texttt{Date} header,
formatted deep inside Nginx from its cached time, is byte-identical on live and recovered instances
across a multi-second gap.

\subsection{Randomness virtualization}
\label{sec:rng}
A server's randomness reaches it by paths that defeat library interposition: V8/Node.js, OpenSSL,
and \texttt{arc4random} issue the \emph{raw} \texttt{getrandom} syscall, and Redis~6 seeds its
SipHash dictionary hash by reading \texttt{/dev/urandom} through \texttt{fopen}, whose internal
\texttt{openat}/\texttt{read} bypass the public symbols. The libOS therefore intercepts at the
syscall level: a seccomp-BPF user-notification filter traps \texttt{getrandom} and fills the buffer
from a deterministic seeded stream, and \texttt{/dev/urandom} is redirected via a private mount
namespace to a deterministic file. This pins every consumer that \emph{routes through} those
interfaces, including OpenSSL's DRBG and Redis's SipHash seed, whose
\texttt{SPOP}/\texttt{SRANDMEMBER} order recovers identically where a real-device control differs
entirely. One consumer is instructive: V8's \texttt{Math.random} seeds from the \texttt{RDRAND}
instruction, which takes no syscall and bypasses both traps (the \texttt{RDRAND} hole of
\S\ref{sec:limits}); we pin it at the layer that owns it, a recorded V8 \texttt{--random-seed} launch
flag, in the same class as \texttt{setarch -R} for address-space layout. The lesson is that the
determinism boundary is per-\emph{consumer}, not per-interface (Appendix~\ref{app:libos}).

\subsection{Threads: deterministic scheduling vs.\ share-nothing sharding}
\label{sec:threads}
For a multi-threaded server the OS chooses the order threads enter critical sections, so
shared-state evolution is non-deterministic. A Kendo-style~\cite{olszewski2009kendo} deterministic
scheduler lets a thread take a top-level lock only when its logical clock is the global minimum,
making the interleaving a function of the clocks, but it serializes critical sections and collapses
throughput on a contended server (Figure~\ref{fig:threads}a), the wall the
deterministic-multithreading literature~\cite{olszewski2009kendo,bergan2010coredet} and
execute-then-verify SMR~\cite{kapritsos2012eve,guo2014rex} sidestep only by relaxing strict
determinism. The practical answer is \emph{share-nothing sharding}, which high-performance servers
already use: $N$ single-thread instances, each deterministic by construction, with no lock
contention, out-throughputting one multi-worker process while staying deterministic
(Figure~\ref{fig:threads}b); the deterministic scheduler remains the fallback for genuinely shared
mutable state. Single-thread servers still spawn timer-driven maintenance threads (e.g.\ Memcached's
LRU maintainer); we disable these so the shard's state evolves purely from the request stream and
the virtual clock.

\subsection{Process-state checkpoint and bounded recovery}
\label{sec:criu}
Replay from process start costs time linear in the log length; a checkpoint bounds it to the
post-checkpoint tail. An application-native snapshot (a Redis RDB) plus tail-replay works for a
single process. The general, any-binary mechanism is CRIU~\cite{criu} (in the userspace-checkpoint
lineage of DMTCP~\cite{ansel2009dmtcp} and BLCR~\cite{hargrove2006blcr}): it checkpoints the whole
process, namely memory, file descriptors, threads, \emph{and} the in-memory virtual clock, so a
restore needs no replay of pre-checkpoint history. We verify CRIU checkpoint/restore of the hardest
app class, a multi-process PostgreSQL (postmaster plus background workers, SysV and POSIX shared
memory, WAL): data is byte-identical across the crash and the restored server is live
(\S\ref{sec:eval-recovery}). PostgreSQL exercises the \emph{checkpoint/restore} path, not
deterministic replay: a shared-everything database has cross-process non-determinism (shared-buffer
access order across backends) that neither sharding nor a per-process virtual clock removes, so it lives
in the \emph{checkpoint-only} regime Remus and HyCoR also occupy, while the four single-thread servers
take the order-log-free replay path (\S\ref{sec:limits}).

\subsection{Output suppression and exactly-once}
On replay the server re-emits outputs it already sent before the crash. The libOS suppresses
these via a per-client \texttt{(client, seq)} high-water-mark, the exactly-once-RPC mechanism of
RIFL~\cite{lee2015rifl} applied to recovery: an output whose sequence is at or below the client's
last acknowledged sequence is dropped, so each acknowledged effect is externalized exactly once.
The high-water-mark map is itself durable, captured in every timestamp-$T$ snapshot and
reconstructed by the same dedup fold that replays the log, so suppression survives a crash that
loses all volatile state. The resulting exactly-once and no-lost-acknowledged-write invariants are
machine-checked in TLA+ (\S\ref{sec:impl}, Appendix~\ref{app:tla}). This is \emph{server-side}
suppression; end-to-end exactly-once additionally requires the \emph{client} to carry a stable identity
across the reconnect a primary failure forces, RIFL's cooperating-client assumption, which the closed
fabric satisfies (a client is a fabric endpoint with a durable id) but a stock external TCP client
reconnecting on a fresh 5-tuple does not (\S\ref{sec:limits}).

\section{Fault Tolerance over the Fabric}
\label{sec:ft}

The engine that ties the libOS to the fabric is a deterministic-replay state machine with a
durable ordered log and timestamp-$T$ snapshots (Algorithm~\ref{alg:ft}). On the live path it
applies fabric-delivered inputs in \texttt{msg\_ts} order, appends \texttt{(ts, op)} to the
durable log, scatters each input to the backup replicas in one RTT, and releases an output only
once the reliable-delivery commit barrier has passed its producing input's timestamp, that is,
once that input prefix is replicated (point (c) of \S\ref{sec:overview}). When the barrier passes
a snapshot timestamp $T$ it takes an uncoordinated empty-channel checkpoint (point (b)). On
recovery, a replacement replica loads the latest snapshot, replays the durable log suffix in
timestamp order (no order-log), and state-transfers any prefix it is still missing from a surviving
replica up to the live cut. Replay runs the same transition function with side effects disabled
(the \textit{live} flag of Algorithm~\ref{alg:ft}); the per-client high-water-mark drops every
output the suffix re-applies, so the replayed effects are exactly-once.

\paragraph{Membership, durability, and recovery.} The configuration is $k$ replicas; each input is
scattered to all $k$ at its total-order position, so it is durable once held by any survivor:
in-memory $f$-of-$k$ fail-stop tolerance. Membership rides on the fabric: 1Pipe's failure detector
(tens of microseconds) excises a dead peer and the survivors' commit barrier resumes over the
reduced membership. Recovery converges only while replay outruns the live stream, so the recovering
replica uses the fabric's barrier-hold as backpressure, which roughly doubles the live rate a
recovery can outrun (Appendix~\ref{app:eval}); the real engine's recovery under concurrent client
load is exercised by the crash-injection test of \S\ref{sec:eval-correct}. A real-hardware
saturation sweep and automated primary-promotion / view-change are future work (\S\ref{sec:limits}).

\begin{algorithm}[tb]
\small
\caption{OneBarrier live and recovery paths (per replica).}
\label{alg:ft}
\begin{algorithmic}[1]
\Procedure{OnDeliver}{$(\mathit{ts}, \mathit{op})$, \textit{live}}\Comment{fabric delivers in \texttt{ts} order}
  \State $\mathit{log}.\textsc{append}(\mathit{ts}, \mathit{op})$
  \If{\textit{live}}\Comment{durability: every live input is replicated}
     \State scatter input to replicas at \texttt{ts} (1 RTT, 1Pipe replication)
  \EndIf
  \State $\mathit{out} \gets \textsc{Apply}(\mathit{op})$\Comment{deterministic state transition}
  \If{$\mathit{out}.\mathit{seq} > \mathit{hwm}[\mathit{out}.\mathit{client}]$}\Comment{not yet externalized}
     \State $\mathit{hwm}[\mathit{out}.\mathit{client}] \gets \mathit{out}.\mathit{seq}$
     \If{\textit{live}} release $\mathit{out}$ once commit barrier passes \texttt{ts}\Comment{output commit}
     \EndIf
  \EndIf\Comment{on replay, suppressed outputs are dropped: exactly-once}
\EndProcedure
\Procedure{OnBarrier}{$T$}\Comment{commit barrier passes snapshot point $T$}
  \State quiesce inputs $> T$; drain handlers $\le T$; \textsc{Checkpoint}($T$)\Comment{empty-channel cut}
\EndProcedure
\Procedure{Recover}{}
  \State \textsc{Load}(latest snapshot)\Comment{restores state \emph{and} $\mathit{hwm}$}
  \State import a survivor's state for any prefix still missing, up to the live cut
  \State \textbf{for} each $(\mathit{ts}, \mathit{op})$ in $\mathit{log}$ suffix in \texttt{ts} order: \textsc{OnDeliver}($(\mathit{ts},\mathit{op})$, \textit{live}$=\textsc{false}$)
  \State resume live delivery (\textit{live}$=\textsc{true}$) past the recovered cut
\EndProcedure
\end{algorithmic}
\end{algorithm}

\section{Implementation}
\label{sec:impl}

The OneBarrier engine is $\sim$4.8\,k lines of Rust over the \texttt{ReliableHost} fabric of an
open 1Pipe reproduction, implementing the key/value state machine, the durable ordered log,
timestamp-$T$ snapshots, exactly-once output suppression, and crash recovery. The production servers
(RESP/Redis, Memcached, HTTP, a transactional store, a pub/sub log), the fault injectors, and the
correctness checkers ship as runnable binaries, and each evaluation result is guarded by a named unit
test that asserts the property under test. The libOS is three \texttt{LD\_PRELOAD} C libraries
(\texttt{libobpreload} for sockets/time/capture, \texttt{librngdet} for the seccomp randomness trap,
\texttt{libdetsched} for deterministic scheduling). We machine-check the core protocols in TLA+:
1Pipe total order (TLC explored $3.5\times10^6$ states with no order violation) and OneBarrier's
exactly-once and no-lost-acknowledged-write properties. The TLA+ models verify the \emph{protocol
abstractions}, not the Rust and C implementations, which are validated separately by the
crash-injection and linearizability checks of \S\ref{sec:eval-correct}. Every result is reproduced by
a single command (Appendix~\ref{app:repro}).

\section{Evaluation}
\label{sec:eval}

We lead with what is measured on real, unmodified binaries (recovery fidelity, correctness under fault,
recovery time, steady-state cost), then quantify the barrier coincidence \S\ref{sec:overview} establishes
by construction and the resource cost against prior systems.

\subsection{Byte-identical recovery of five unmodified servers}
\label{sec:eval-recovery}
The test of ``transparent'' is binary: kill an unmodified server, wait a real wall-clock gap,
recover it, and demand the bytes match. Four servers take the deterministic-replay path (record under
the virtual clock and randomness stack, \texttt{kill -9}, wait, replay on a fresh instance), while
PostgreSQL, shared-everything and so not a replay candidate, takes the general CRIU path. Each passes
on the strongest reading: not merely a time-derived header but full \emph{state} reconstructs
identically (Figure~\ref{fig:recovery}), covering Redis TTL expiries, Node.js session IDs keyed by
\texttt{Math.random()}/\texttt{Date.now()}, Memcached's LRU eviction order, and PostgreSQL's
multi-process on-disk tree, while a no-libOS control diverges: determinism here is something the
libOS manufactures.

\subsection{Correctness under fault}
\label{sec:eval-correct}
Byte-identity shows the recovered state equals the recorded one; it does not show that state was ever
\emph{consistent}. Two complementary checks close that gap on a recovered unmodified Redis crashed
mid-load under eight concurrent clients. Mass survival: every acknowledged write reappears after
recovery with its exact value, $191{,}073$ acked, $0$ lost, $0$ torn, with in-flight operations
excluded as the honest output-commit gap. And a genuine verdict: a from-scratch Wing--Gong
linearizability~\cite{herlihy1990linearizability} checker searches the real-time-overlapping history
of a contended register, including the post-recovery read, and certifies it linearizable. We keep the
two distinct: survival scales to many operations, while the verdict is a search exponential in
concurrency, decidable only on a small history (Appendix~\ref{app:eval}).

\subsection{Recovery time and steady-state cost}
\label{sec:eval-time}\label{sec:eval-overhead}
Two costs decide deployability: recovery time and steady-state overhead. Recovery is affine in the
replayed log length above a fixed restore floor (Figure~\ref{fig:rectime}), and a checkpoint caps the
replayed suffix to the post-checkpoint tail, so downtime is a tunable parameter held well under the
seconds-to-minutes of detect-and-restart cluster failover. In steady state the virtualization a server
exercises is cheap, a few percent or less (Figure~\ref{fig:overhead}), because each interceptor is a thin
shim over a syscall the server already makes. The one costly mechanism is deterministic scheduling, whose
serialization is fundamental, which is why the production path is share-nothing sharding
(\S\ref{sec:threads}).

\subsection{The barrier coincidence, measured}
\label{sec:eval-overlap}
\S\ref{sec:overview} argues that output commit and reliable delivery are the \emph{same} barrier. The
question an experiment can settle is binary: does the durable write \emph{ride} the barrier the fabric
already crosses, or \emph{stack} on top of it? We isolate the marginal durability cost of FT under two
tiers (Table~\ref{tab:rq2}): in-fabric replication, which should ride, and serial fsync-to-storage,
which cannot.

In-fabric replication rides: the durable write completes inside the commit barrier and its marginal cost
is a rounding error on delivery latency (Figure~\ref{fig:overlap}). Serial fsync stacks: it roughly doubles
commit latency and saturates the executor, reproducing the output-hold failure mode that sank Remus. The
loopback baseline is itself millisecond-scale, so what it establishes is the \emph{structure}, ride versus
stack. That this carries to the microsecond operating point follows by construction (\S\ref{sec:overview})
and is corroborated two ways: a discrete-event model at 1Pipe's parameters, whose FT-overlap tail is
indistinguishable from the reliable-fabric baseline at every load (Figure~\ref{fig:loadsweep}), and real
RDMA verbs whose one-sided-write latency sits in the assumed band (Appendix~\ref{app:model}). Only a hardware
RDMA/P4 testbed would put a direct number on the avoided cost; the coincidence does not depend on one.

\section{Generality: Beyond the Five Servers}
\label{sec:ext}
Is the mechanism only ``request/response store with in-memory state''? The design itself says where it
generalizes, through a fit-test that is its preconditions read forward: an unmodified server extends
transparently if it is deterministic given input order, share-nothing or cleanly shardable, socket-based,
and bounded in output. The test routes each application to order-log-free deterministic replay (for
share-nothing socket servers) or general CRIU checkpointing (for any shared-everything binary,

network function, a stateful microservice, and infrastructure daemons) recover exactly-once and

entry IDs and consumer offsets byte-identically, contesting exactly-once stream processing, and an

shared-everything concurrency, not ``databases.'' And one discovery: the determinism unit is the message,
not the connection, so it was \emph{UDP} servers like dnsmasq, not TCP ones, that needed a fix, the
opposite of the usual assumption.

\section{Limitations and Scope}
\label{sec:limits}

\textbf{No RDMA/P4 hardware.} The fabric's RDMA \emph{latency} is reproduced in a model
(Appendix~\ref{app:model}) and corroborated by CPU-bound SoftRoCE verbs, so the overlap is established by
the model rather than measured on hardware, the only major claim not measured on real artifacts.
\textbf{Durability model.} Durability is in-memory $f$-of-$k$ fail-stop tolerance via in-fabric
replication, not crash-consistent persistence across correlated power loss (the FaRM/RAMCloud
tradeoff~\cite{dragojevic2014farm}). \textbf{No automated failover.} We validate the recovery
\emph{mechanism} and inherit membership from the fabric's failure detector, but leave the
primary-promotion / view-change protocol (e.g.\ Viewstamped Replication~\cite{oki1988vr,liskov2012vrrevisited})
to a production layer; because the design is passive, a primary failure incurs a recovery window of
unavailability, the price of holding execution CPU near a single replica's.
\textbf{Shared-everything determinism.} Order-log-free replay is for share-nothing servers; arbitrary
shared-everything multithreading falls back to the checkpoint-only CRIU path (\S\ref{sec:criu}).
\textbf{Residual non-determinism.} Two userspace instructions take no syscall and export no symbol:
\texttt{RDRAND} (pinned per-consumer here) and \texttt{RDTSC} (used by none of our five servers). A fully
general guarantee would trap both via \texttt{prctl} and instruction-trap paths (Appendix~\ref{app:libos}).
\textbf{Cooperating peers and clients.} The deepest boundary is an impossibility, not a cost: transparent
FT cannot un-send an external side effect already delivered to a peer that will not cooperate. Output
commit \emph{bounds} the inconsistency window but does not eliminate it, so the clean wins are
fabric-internal, idempotent, and self-contained leaf services; a non-cooperating peer is served correctly
only by buffering output at the ingress until durable, re-importing the latency the design removes.

\section{Related Work}
\label{sec:related}

\paragraph{Transparent fault tolerance.} Whole-machine replication makes unmodified workloads
fault-tolerant, from hypervisor FT~\cite{bressoud1995hypervisor} through Remus~\cite{cully2008remus}
(checkpoint-and-buffer), VMware FT~\cite{scales2010vmwareft} (lock-step), COLO~\cite{dong2013colo}, and
Crane~\cite{cui2015crane}. Closest to us, LLFT~\cite{zhao2013llft} replays unmodified socket apps with no
order-log via totally-ordered virtual time, and HyCoR~\cite{zhou2021hycor} (successor
RRC~\cite{zhou2022rrc}) gives checkpoint-plus-replay FT for unmodified containers while still logging
non-determinism over a normal network; OneBarrier relocates both order and durability into an in-network
fabric.

\paragraph{Deterministic replay and SMR.} ReVirt~\cite{dunlap2002revirt}, rr~\cite{ocallahan2017rr}, and
Castor~\cite{mashtizadeh2017castor} record non-determinism for replay, the dominant cost being
shared-memory access order, which OneBarrier instead sources from the fabric. SMR~\cite{schneider1990smr}
feeds deterministic replicas a totally-ordered input from consensus (Paxos~\cite{lamport1998parttime},
Raft~\cite{ongaro2014raft}); a recent line offloads ordering to the network for \emph{active} SMR
(NOPaxos~\cite{li2016nopaxos}, Eris~\cite{li2017eris}, Derecho~\cite{jha2019derecho}) using programmable
switches~\cite{bosshart2014p4} and logical clocks~\cite{lamport1978time}. 1Pipe~\cite{li2021onepipe} instead
provides total-order \emph{communication}, which we repurpose as a \emph{passive}-FT substrate.

\paragraph{Durable execution, checkpoint, and DMT.} The industrial path rewrites applications to
externalize state: durable execution (Temporal~\cite{temporal}, DBOS~\cite{skiadopoulos2021dbos}),
exactly-once stream processing (Flink~\cite{carbone2015flink}), and deterministic databases
(Calvin~\cite{thomson2012calvin}) that sequence transactions up front, the database-layer analogue of
OneBarrier's fabric-supplied order but requiring a rewrite. CRIU~\cite{criu} checkpoints unmodified
processes (we use it for bounded recovery), as do microVM snapshot
systems~\cite{agache2020firecracker,ustiugov2021reap} and gVisor~\cite{gvisor}, the closest prior point to
our libOS+app snapshot. Kendo~\cite{olszewski2009kendo} and dThreads~\cite{liu2011dthreads} make
multithreading deterministic at the throughput cost that motivates our sharding, and execute-then-verify
replication~\cite{kapritsos2012eve,guo2014rex} reaches multicore replication only by relaxing strict
determinism.

\paragraph{Library OS, output commit, and correctness.} SocksDirect~\cite{li2019socksdirect} is the
lineage of our user-space socket interception, FastWake~\cite{li2023fastwake} the completion-wait mechanism,
and Arrakis~\cite{peter2014arrakis} and Demikernel~\cite{zhang2021demikernel} give applications fast
datapaths; the microsecond operating point is set by RDMA systems such as FaRM~\cite{dragojevic2014farm}
(whose replication-vs-power-loss tradeoff we adopt) and eRPC~\cite{kalia2019erpc}. The problems we inherit
are old: output commit~\cite{strom1985optimistic}, consistent snapshots~\cite{chandy1985snapshots},
synchronized-clock external consistency~\cite{corbett2012spanner,geng2018huygens}, and
linearizability~\cite{herlihy1990linearizability}.

\section{Conclusion}

Transparent fault tolerance failed to ship because three coupled costs (order logging, the distributed cut,
and output commit) were large at the millisecond operating point, not because snapshots are hard. The
verdict is operating-point-dependent. A determinism libOS makes unmodified Redis, Memcached, Nginx,
Node.js, and PostgreSQL recoverable at a few-percent overhead, and an in-network total-order reliable
fabric collapses all three costs into mechanisms it already runs for communication correctness. At the
microsecond operating point, transparent fault tolerance becomes a byproduct of the communication fabric.

\section{libOS Implementation Details}
\label{app:libos}

\paragraph{Virtual clock.} Listing~\ref{lst:vclock} shows the interceptor: at each input event time
advances by the real inter-arrival delta, logged live and replayed on recovery, so every time read is
wall-clock-faithful and a deterministic function of the input prefix. The unit is one delivered message,
not one TCP segment: the fabric hands the server one message per \texttt{recv}, so record and replay
consume the identical sequence of reads. The one residual is that time advances only at input events, so a
fully idle server's clock is frozen between requests and a TTL due in an idle gap is observed lazily, at
the next input; the value is correct, only the moment deferred. The vDSO is no escape hatch because
\texttt{LD\_PRELOAD} overrides the exported symbols.

\begin{lstlisting}[style=cstyle,caption={The virtual clock: at each input event time advances by the
\emph{real} inter-arrival delta, logged live and replayed on recovery, so every time read is
wall-clock-faithful \emph{and} a deterministic function of the input prefix. (Over the fabric, \texttt{delta}
is read from the message's total-order timestamp rather than measured.)},label={lst:vclock},float=h,
basicstyle=\ttfamily\footnotesize]
ssize_t recv(int fd, void *b, size_t n, int fl) {
  ssize_t r = real_recv(fd, b, n, fl);
  if (r > 0 && is_conn(fd)) {           // a deterministic input event:
    long long delta = recording        //   wall-clock delta since last input,
        ? log_delta(now() - last)       //   measured + logged live, or
        : replay_delta();               //   replayed from the log on recovery
    atomic_fetch_add(&ticks, delta);    //   advance virtual time by it
  }
  return r;
}
int clock_gettime(clockid_t c, struct timespec *t) {
  long long v = base_ns + atomic_load(&ticks);  // base persisted at record
  t->tv_sec = v / 1000000000; t->tv_nsec = v % 1000000000;
  return 0;                        // same inputs+deltas -> same time
}
\end{lstlisting}

\paragraph{The \texttt{RDRAND}/\texttt{RDTSC} holes.} Time and randomness are virtualized through the
libc, syscall, and device-file surfaces, but two userspace instructions take no syscall and export no
symbol. \texttt{RDRAND} feeds OpenSSL (masked via \texttt{OPENSSL\_ia32cap}) and V8's \texttt{Math.random}
seed; the \texttt{getrandom} trap never sees that seed, so we pin it at the V8 layer with a recorded
\texttt{--random-seed}. \texttt{RDTSC} (the timestamp counter) is used by none of our five servers for
externally-visible time but is not yet generally pinned. A fully general guarantee would trap both,
\texttt{RDTSC} via \texttt{prctl(PR\_SET\_TSC)} and \texttt{RDRAND} via the same instruction-trap path, and
emulate them from the virtual clock/seed.

\paragraph{Engineering realities.} Making ``unmodified'' credible meant handling the awkward edges of
interposition: the \texttt{LD\_PRELOAD} early-init trap, glibc symbol versioning (e.g.\ \texttt{pthread\_%
cond\_wait} must be \texttt{dlvsym}-bound to \texttt{GLIBC\_2.3.2}, since plain \texttt{dlsym} returns the
old compat shim and hangs threaded servers), a seccomp filter whose supervisor lives in the very process it
traps, and disabling Memcached's timer-driven maintenance threads. These are not incidental: they are why
library-level interposition misses the raw-syscall and internal-call paths real servers actually use.

\section{Additional Evaluation Detail}
\label{app:eval}

\paragraph{Recovery fidelity and correctness.} Under fault (\S\ref{sec:eval-correct}), $191{,}073$
acknowledged writes survived recovery with $0$ lost and $0$ torn, and the Wing--Gong verdict is rendered on
the $33$-operation contended-register history including the post-recovery read. Determinism is robust rather
than a lucky single run: across $25$ independent record/crash/replay trials of redis (TTL state) and $8$ of
Node.js (session state derived from \texttt{Math.random()} \emph{and} \texttt{Date.now()}), the recovered
state was byte-identical to live in \emph{every} trial while a no-libOS control diverged in every trial.

\paragraph{Recovery under sustained load.} A recovering replica restores its snapshot and replays the
durable log forward to the live cut, converging only while replay outruns the live stream
(Figure~\ref{fig:recovery_load}). Plain replay livelocks once the live rate reaches replay capacity, while
the fabric's barrier-hold backpressure throttles senders to the recovering node and roughly doubles the load
a recovery can outrun. This is a closed-form catch-up model, labelled as such; the real engine's recovery
under concurrent client load is measured by the crash-injection test (\S\ref{sec:eval-correct}), and a
real-hardware saturation sweep remains future work.

\section{Generality: The Full Study}
\label{app:ext}
This appendix expands \S\ref{sec:ext} with the per-class detail behind Figures~\ref{fig:taxonomy}
and~\ref{fig:extresults}. The fourth fit-test precondition, bounded output, is an output-commit
requirement: suppression keys each externalized effect by a per-client high-water-mark, so an application
whose response is an unbounded stream has no sequence point at which the effect is acknowledged and
replay-suppressible. Request/response and discrete-message workloads satisfy it; an infinite server-push
stream does not.

\paragraph{Message brokers contest exactly-once streaming.} A broker's job, total order plus durable
delivery, is what the fabric already provides. A stock \texttt{redis-server} used as a stream broker recovers
its entry IDs and consumer offsets byte-identically, because a Redis stream auto-ID (\texttt{<ms>-<seq>})
derives from the server clock the virtual clock determinizes, the streaming-log analogue of the Nginx
\texttt{Date} header. The Kafka \emph{partition} model \emph{is} our share-nothing sharding, $N$
single-thread partitions each with its own log, so a killed partition recovers byte-identically with offsets
preserved while publish throughput scales near-linearly (Figure~\ref{fig:partscale}). Stock Mosquitto carries
the result to MQTT, recovering its retained-message store by replaying the publish stream.

\begin{figure}[h]
\centering
\includegraphics[width=0.5\linewidth]{figures/fig_partition_scale.pdf}
\caption{Kafka partition model: $N$ share-nothing single-thread partitions scale publish throughput
near-linearly (the partitions share nothing, so there is no contention to serialize), reaching $7.9\times$ at
$8$ partitions (the $4.1\times$ point at $4$ partitions is measurement noise around linear).}
\label{fig:partscale}
\end{figure}

\paragraph{A database on the replay path, not just the checkpoint path.} PostgreSQL recovered only via CRIU
(\S\ref{sec:criu}) because it is shared-everything. SQLite is single-threaded, so a stock \texttt{python3}
process on the stdlib \texttt{sqlite3} module recovers by order-log-free \emph{deterministic replay}: rows
from SQLite's own time (\texttt{strftime}) and PRNG (\texttt{random()}, seeded from \texttt{/dev/urandom}) are
byte-identical across a crash where a control differs in both. This first SQL database on the replay path
shows the boundary is shared-everything concurrency, not ``databases.'' The CRIU path covers the rest:
PostgreSQL's multi-process tree and a multi-threaded MySQL/MariaDB, both checkpoint/restored byte-identically
with the server live.

\paragraph{Stateful network functions: FT as ordered replay.} An NF is a deterministic packet-processing
state machine, so its flow state is recoverable by replaying the fabric-ordered packet log, the
FTMB/Pico-Replication stateful-middlebox problem~\cite{sherry2015ftmb,rajagopalan2013pico}. A software Click
NF of ClickNP-style~\cite{li2016clicknp} elements (a \texttt{FlowCache} table plus an L4 load-balancer), fed
packets over a socket, recovers its flow table (each flow's backend affinity \emph{and} conntrack last-seen
timestamp) byte-identically, where a control's timestamps differ. A stateless restart cannot reconstruct
this, which is the whole problem stateful-NF-FT exists to solve.

\paragraph{Stateful microservices contest durable execution.} Durable execution (Temporal, DBOS) rewrites a
service to externalize its state and non-deterministic effects. OneBarrier gives an unmodified order/checkout
microservice the same guarantees transparently: across a crash the order book recovers exactly-once \emph{and}
byte-identically, including the random order ids and timestamps a rewrite would externalize by hand, while a
control differs. The honest boundary (\S\ref{sec:limits}): a service that calls \emph{other} non-cooperating
services cannot un-send those effects, so the clean wins are leaf, self-contained services.

\paragraph{Network-infrastructure servers, and a UDP generalization.} The ubiquitous single-process daemons
fit directly: lighttpd and HAProxy recover their HTTP \texttt{Date} header byte-identically as Nginx does, and
dnsmasq's cached-record TTL recovers byte-identically under the virtual clock while a control tracks real
time. dnsmasq also exposed a boundary: DNS is \emph{UDP}, but the clock ticked only on TCP reads. A six-line
extension to tick on \texttt{recvfrom}/\texttt{recvmsg} makes single-process UDP servers deterministic,
leaving prior results unchanged. (dnsmasq's TCP path forks per query and resets the tick counter, so UDP is
the deterministic path, the opposite of the usual assumption.)

\paragraph{Cross-shard atomicity is the same primitive.} The obvious objection to sharding is multi-key
atomicity, which the fabric answers for free: a 1Pipe scattering delivers a group to different destinations at
one total-order position, atomically (\S\ref{sec:why}), a multi-shard transaction without application-level
two-phase commit. The same primitive that makes one input durable across replicas makes a multi-shard write
atomic across shards. We note this as a design consequence, not a measured result.
